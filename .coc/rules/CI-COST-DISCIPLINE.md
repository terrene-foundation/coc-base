# CI Cost Discipline — A Gate Run Is A Purchased Resource, And The Dominant Waste Is Re-Pushing

Full examples, instruments, prohibition recap and evidence: `.claude/guides/rule-extracts/ci-cost-discipline.md`. The seven clauses below remain the governing contract.

Re-pushing spends an in-flight verdict and queue position. Measure queue wait separately from execution time and use a large observation window; the full evidence and sampling corrections are in the companion.

Depth — the full measurement, the per-branch breakdown, the revert-safety decision procedure, the merge-queue variants, and the cross-repo (build / use / downstream) mapping — is `.claude/skills/30-claude-code-patterns/ci-cost-discipline-evidence.md`.

## MUST Rules

### 1. Do Not Push Again To An Open PR To Find Out Whether It Passes

Once a PR is open, every further push to its branch CANCELS the in-flight run and starts a fresh one from zero. The agent MUST establish locally that the change passes before each push — not only the first — using the project's CI-parity command set, which `git.md` § "Pre-FIRST-Push CI Parity Discipline — SCOPED By Default" already specifies (cited, not restated, per `specs-authority.md` Rule 9): that set is **scoped to the diff by default**, derived from `git diff --name-only`, with the unscoped whole-repo run reserved for the five junctures that earn it. That clause governs the FIRST push; this one extends the same obligation to EVERY subsequent push, at the same scope. Pushing a change whose local verification has not been run, in order to let CI report the answer, is BLOCKED.

**DO:** derive affected packages from `git diff --name-only`, run their CI-parity gates locally, then push once. **DO NOT:** push an unverified fix and wait for CI to discover the lint failure.

**BLOCKED rationalizations:**

"CI will tell me faster than running it locally" (heavy-job wall-clock p50 47 min, p90 183.5 min — it does not) · "The run was going to fail anyway, so cancelling it costs nothing" · "Cancelled runs cost nothing" (one cancelled mid-EXECUTION is billed for the wall-clock it consumed — `git.md`; one cancelled while QUEUED cost its author the entire wait and held a queue slot) · "It is a one-line fix, not worth a local run" (a one-line diff scopes to a one-line gate — an argument for running it, not for skipping it) · "I will push now and fix lint in a follow-up commit" · "The reviewer is waiting, pushing is the responsive thing to do" · "Pre-flighting is slower" — BLOCKED in its SKIP form only. The pre-flight's duration is [UNMEASURED — no local timing instrument is cited here]; what IS measured is the thing it replaces, a fresh full-run wait averaging 20.8 min, p50 47 min on the heavy job. The claim that survives without a local number is the ORDERING: bounded and synchronous beats unbounded and asynchronous. · "The full local set takes too long, so I will push and let CI answer" (the skip loses the ANSWER; the question survives it) · "I will just run the tests that look relevant" (a judgment-chosen subset is the `owed-suites.mjs` failure mode — derive the subset from the diff)

**NOT a rationalization — this is the EXPECTED move, and pricing it as one was this corpus's own error:** _"the full set is unscoped for this diff, so I will run the gate over what the diff touches, and take the full run only at a juncture that earns it."_ Scoping narrows the gate's INPUT; skipping removes its OUTPUT. Only the second is BLOCKED. `git.md` § "Pre-FIRST-Push CI Parity Discipline — SCOPED By Default" owns the scoped command sets and the five earning junctures.

**Why:** This is the dominant measured waste — **1,165 of the 1,208 destroyed wall-clock minutes (96.5%), across 78 re-pushes averaging 14.9 minutes each**. **Be precise about what it wastes:** those runs are largely cancelled while still queued, executing zero steps, so the saving is NOT runner capacity and claiming it would be an over-claim. What the re-push destroys is an in-flight verdict, a fresh wait for its author, and a position in the queue that is 78% of elapsed time on a saturated pool. A local pre-flight answers the same question synchronously and at a bounded cost; its duration here is [UNMEASURED — no local timing instrument is cited here], and a figure was previously printed as though it had been measured. Scoping it to the diff is what keeps that cost bounded.

### 2. One PR Per Wave, Bounded By REVERT-SAFETY — Not By A Count

A wave's changes MUST be consolidated into ONE PR **if and only if** the whole diff is independently revertible as a unit — reverting it leaves the tree coherent and removes exactly one decision. Changes that are NOT jointly revert-safe MUST still split, however many PRs that yields. Opening a PR per shard when the shards ARE jointly revert-safe is BLOCKED; bundling unrelated work to hit a PR count is equally BLOCKED. There is deliberately no numeric cap: a cap forces unrelated work together and makes the revert dangerous, which costs more than the CI it saves.

**DO:** combine three jointly revert-safe fixture shards into one PR; keep a guard fix and unrelated manifest re-tier separate. **DO NOT:** create one PR per jointly revert-safe shard.

**BLOCKED rationalizations:**

"A separate PR is cleaner for review" (split the REVIEW with commits, not the CI with branches) · "Each shard had its own worktree, so it gets its own PR" · "Smaller PRs merge faster" · "They are logically distinct" (the test is revert-safety, not conceptual tidiness) · "Consolidating means one CI failure blocks everything" (it blocks one revert-safe unit, which is the point) · "The wave plan listed them as separate items"

**Why:** Each additional PR is another entrant in the queue that dominates elapsed time. Measured WALL-CLOCK (queue + execution) is **20.8 minutes** for a successful `pull_request` run against **7.7 minutes** for a `push` run; the execution component alone averages ~11.9 minutes, so what an extra PR mostly buys is queue — exactly the scarce resource. Revert-safety is the correct boundary because it is the only property that makes a bundled PR SAFE to treat as one decision; a count would optimize CI at the cost of the thing CI exists to protect.

### 3. An Amendment To A Queued PR Must Be Worth A Full Run

Amending, rebasing, or force-pushing a PR whose run is queued or in flight discards that run and buys a new one. Before amending, the agent MUST judge whether the change justifies a full run at the measured PR-run cost; changes that do not (a typo in a comment, a reworded PR body line committed into the branch, a cosmetic reorder) MUST be batched with the next substantive push or dropped. Treating an amendment as free because a run was already queued is BLOCKED — the queued run was a purchased position, and the amendment spends it.

**DO:** fold a comment typo into the next substantive push or drop it. **DO NOT:** amend and force-push a queued PR for that typo.

**BLOCKED rationalizations:**

"CI was queued anyway, so the amendment is free" · "Zero wall-clock cost — the run had not started" · "Amending keeps the history clean" · "It is one character" · "The maintainer will ask for it anyway"

**Why:** A queued run is a claimed position in the resource that dominates elapsed time — 78% of it — not a free option; discarding it re-queues behind everything that arrived since. The failure mode is that the cost is reasoned about as marginal _because_ the run had not started, when the un-started run is precisely the one whose whole value was its queue position. "It had not started yet" is not mitigation; it is the loss.

### 4. Merge Cadence — Serialize Or Batch Merges Into A Shared-Concurrency Branch

Where the target branch's workflow uses a shared concurrency group (`${{ github.workflow }}-${{ github.ref }}` or equivalent), merging N PRs in a burst starts N runs of which N−1 are cancelled. Where a merge queue exists, the agent MUST use it; where it does not — the usual case in build / use / downstream repos — merges MUST be serialized or batched rather than fired in a burst.

**A `push:` arm on the default branch buys a POST-MERGE run that is often a duplicate — and where it is NOT a duplicate, it is worse than one. MEASURED at loom, 2026-09-01, over 37 runs / 621 wall-clock minutes.** Post-merge `push: main` runs were **291 min — 47% of the window**. Of 14 merges, **7 produced a tree IDENTICAL to the PR head**: ~**145 min (23%)** that could not have learned anything the PR run had not already reported. The other 7 were the opposite defect, not the same one — base had MOVED, and most PR branches carried exactly ONE run, so **7 merged combinations had never been tested by anything** and main was the first surface to see them. **Zero main runs failed in the window; read that as luck, not as a gate reporting green** — a post-merge run discovers a break after the merge, which is the one moment a gate cannot act on.

Instrument: run `node .claude/bin/check-ci-config-invariants.mjs`; read queue-enabled state, `merge_group` wiring, and plan/visibility separately. `merge queue enabled true` falsifies the claim that the queue is off.

**Three distinct facts, and reading any one for another is `instrument-discipline.md` MUST-4.** _Is a queue ENABLED_ (a ruleset/protection fact), _would the workflows RUN in one_ (an unfiltered `merge_group:` arm), and _may this repo HAVE one at all_ (an ENTITLEMENT fact — on GitHub a merge queue on a PRIVATE repo requires Enterprise Cloud, and non-GitHub hosts have no equivalent). A `merge_group:` arm is INERT until a queue exists, so landing one is safe enabling work and is NEVER itself the remedy. Entitlement is REPORTED by that tool, not PROBED — so where the plan does not carry it, the decision is not "serialize or not", it is a PROCUREMENT question, and surfacing it as a config toggle would be wrong.

**Enabling the queue is an OPERATING-MODEL DECISION and the agent MUST NOT take it alone.** A merge queue tests the POST-MERGE combination BEFORE the merge, which is the run the duplicate was standing in for — so enabling it and dropping the `push:` arm closes BOTH halves at once, the wasted 23% and the untested 7. It is still not a free win, and presenting it as one is BLOCKED. It SERIALIZES merges, adds queue latency to every merge, and an `--admin` merge BYPASSES the queue entirely — so the habit that currently lands PRs would silently defeat it, and adopting the queue means giving up admin-merge as the normal path. Where the instrument above shows the queue wired and switched off, the agent MUST surface the measurement, the trade-off AND the entitlement status as one decision, and PROCEED ON THE OWNER'S ANSWER. Depth — the both-directions trade-off table, the instrument's falsifying result, and what about the queue is deliberately UNMEASURED: `skills/30-claude-code-patterns/ci-cost-discipline-evidence.md` §7c. Enabling a queue, deleting a `push:` arm, or changing the merge method on the agent's own judgment is BLOCKED — these are envelope changes under `autonomous-execution.md` § Structural vs Execution Gates, not the in-envelope root-cause fixes that section authorizes.

**Read your own triggers before applying any clause in this rule — do not inherit loom's.** Every cost claim here rests on a workflow trigger shape (`push:` constrained to the default branch, `pull_request` branch-general, a shared concurrency group with `cancel-in-progress`). That shape is a per-repo fact, not a constant, and where it differs the arithmetic differs — sometimes in sign, not just magnitude. MUST-5's **Instrument A** is the one-line check; run it in THIS repo before treating any figure below as yours.

**DO:** use an available queue (`gh pr merge <N> --auto`); otherwise serialize merges. **DO NOT:** burst-loop `gh pr merge --admin --merge` against shared concurrency.

**BLOCKED rationalizations:**

"Cancellation is the concurrency group working as designed" (it is the group limiting damage, not authorizing the burst) · "The main-branch run is short" (true HERE — see Why; it is a property of this repo's workflow, not a general one) · "Merging is instant, the runs sort themselves out" · "The post-merge run is the real gate" (it reports AFTER the merge, which is the one moment nothing can act on it) · "Main is green, so the duplicate runs are earning their keep" (a window with zero failures cannot distinguish a working gate from an unexercised one) · "The merge queue is obviously right, I will just enable it" (it serializes merges and `--admin` bypasses it — an operating-model change, not a config tidy) · "47% of CI is waste, turning the queue on recovers it" (the 47% is measured; the serialization cost is not, and a one-sided figure is not a decision) · "I will drop the `push:` arm now and raise the queue separately" (that removes the only post-merge check before its replacement exists) · "rulesets came back empty, so nobody wanted the queue" (that command reports whether one EXISTS, never whether the plan PERMITS one) · "the `merge_group:` arm is already in the workflow, so the queue is basically on" (the arm is INERT until a queue exists)

**Why, stated at its MEASURED cost rather than its assumed one:** at loom this clause is nearly free — **41 main-branch cancellations totalling 42 minutes**, about a minute each, because loom's main runs are killed almost immediately by the next merge. It is a MUST anyway because that figure is a property of one repo's workflow shape, not of the mechanism: the same burst against a target whose main-branch job does real work (publish, integration, matrix) destroys N−1 near-complete runs. The clause is scoped to where it bites, and an agent MUST NOT generalize loom's 42 minutes into "burst-merging is cheap" anywhere else.

### 5. Fold A Wave Onto One Integration Branch Only When BOTH Preconditions Measure TRUE HERE

Where a wave's shards are jointly revert-safe (MUST-2), they MAY additionally be folded onto a single integration branch so the wave costs ONE PR run instead of N. The agent MUST evaluate BOTH preconditions **against this repo, by running the instruments**, before folding — and MUST NOT fold when either is false, because under ¬A folding actively costs MORE than not folding.

**Precondition A — is a branch push free here?** Read this repo's own workflow triggers. A is TRUE iff every `push:` arm is constrained to the default branch (or tags only) AND `pull_request` is the only branch-general trigger.

Instrument A: inspect this repo’s workflow `on:` blocks for every `push`, branch/tag restriction and branch-general trigger; the full grep is in the companion. A branch-general `push` makes A FALSE.

Under ¬A every shard push to the integration branch starts its own run, so folding **inverts** into a per-shard cost — strictly worse than one PR per shard, which at least gets `cancel-in-progress` de-duplication.

**Precondition B — is runs-per-PR high enough to be worth the coordination?** Measure it; do not assume it.

Instrument B: run `gh run list --limit 800 --json event,headBranch`, filter `pull_request`, and divide run count by distinct head branches (full pipeline in the companion). A small recent-N window understates repeat runs.

**The decision rule is a comparison, not a constant:** fold when the runs you would SAVE (≈ `runs_per_PR × (shards − 1)`) exceed the coordination cost of carrying an integration branch — one extra branch to keep rebased, one shared review surface, and one revert that takes the whole wave. Two measured anchors for calibration, NOT thresholds: **loom ≈ 3.0** (folding is marginal — a 3-shard wave saves ~6 runs, and the integration branch is often not worth it), and a **sibling BUILD repo ≈ 18** (folding is decisive — the same wave saves ~36 runs). A bare numeric cut-off is deliberately not given: the corpus keeps catching unjustified constants, and the right cut-off depends on a coordination cost this rule cannot measure for you.

**DO:** record A TRUE plus measured B and the saved-runs/coordination comparison before folding; A FALSE means do not fold. **DO NOT:** inherit another repo’s numbers or fold because the wave feels big.

**BLOCKED rationalizations:**

"The sibling repo measured this, so it holds here" (A and B are per-repo; that is the whole point of the clause) · "Folding is always cheaper" (false under ¬A, where it inverts) · "I'll assume runs-per-PR is high, it feels high" (measure it — and at `--limit 100` it will read ~2× low) · "Precondition A is obviously true, every repo gates push to main" (it is not; unconstrained `push:` arms are common in consumer repos) · "One integration branch is free coordination"

**Why:** the mechanism is real and was measured at a consumer, not here — a BUILD sibling at ~18 runs/PR, where folding a wave is decisive. But it does NOT generalize unconditionally: it rests on a branch push being free, which is a property of the workflow's trigger shape and false wherever `push:` is branch-general. Shipping it unconditionally would hand every consumer a change that silently inverts in exactly the repos whose CI is already worst. Both preconditions are cheap to evaluate, so making them mandatory costs one `grep` and one `gh run list` against a wave that would otherwise cost N full runs.

### 6. A Saturated LOCAL Pool Is Surfaced As A CHOICE Before The Push, Never Discovered In The Queue

When a push would trigger CI and the self-hosted pool **that this repo's own workflows request** has ZERO idle runners, the session MUST surface the choice BEFORE pushing — queue to local, or spend GitHub-hosted minutes — and proceed on the operator's answer. Pushing into a measured-full pool without surfacing it is BLOCKED, and so is switching a job's `runs-on` to a hosted runner without saying so.

**Saturation is ZERO idle in the REQUESTED pool.** Not "few idle", and not an org-wide count: an org-wide tally reads _capacity available_ off idle runners in a pool the job cannot use, which is silence on exactly the saturation this clause exists to catch (`instrument-discipline.md` MUST-4 — an instrument is scoped to the question it was BUILT for).

**A grant is bounded or it is not a grant.** A session-level blanket MUST carry an expiry — explicit, or a bounded default — and MUST state a reason; an empty file is not a grant, an unparseable expiry fails CLOSED, and an expired one stops working. It clears the ASKING only: it authorizes no `runs-on` edit and no other spend.

**A hosted switch carries a revert obligation, tracked.** Changing `runs-on` lands on the default branch unless reverted, silently moving every future run onto billed minutes. And a job pinned to a self-hosted pool may be pinned for a REASON — read the pin's comment before proposing the move.

**DO:** report zero idle in the requested pool, offer local queue versus billed hosted capacity, and track the switch’s revert obligation. **DO NOT:** push into that pool or switch `runs-on` silently.

**BLOCKED rationalizations:** "it will probably get a slot" · "the queue is someone else's problem" · "hosted runners are cheap, just switch it" · "I'll revert the runs-on before merge" (unless it is tracked, that is a memory, not an obligation) · "some runners are idle" (in a pool this job cannot use) · "the pin is stale, nothing depends on it" (read the comment first) · "I already asked once this session" (a grant without an expiry is not a standing policy).

**Why:** Queue wait, not execution time, is the dominant cost when the local pool is full — a run that queues an hour and then executes in 45 seconds spent the hour for nothing, and the session that pushed it cannot see the queue from inside. Surfacing it before the push converts an invisible hour into a decision that costs one sentence.

### 7. A Shared Machine's CPU Is Bought Like A CI Run — Synthetic Load Is BLOCKED

Every session on a shared machine spends from one CPU pool, as every push spends from one runner pool. Generating synthetic CPU load there — a stress tool, a busy loop, N parallel burners — is BLOCKED, including to prove a flake is load-related. A load- or timing-dependent failure is a DETERMINISM bug and MUST be reproduced by forcing the budget, injecting a clock, or stubbing the slow call (`testing.md` § "Never Assert An UPPER Bound On Real Elapsed Time" owns the clock techniques). A heavy run — full suite, gate, mutation sweep — MUST NOT start while the 1-minute load average exceeds the core count: read it first. A duplicate pre-run of a gate that must run again anyway MUST NOT be started at all.

**DO:** force the budget the flake depends on to its failing value and watch the same cases fail on every run; read `uptime` before the one heavy run and hold it while load exceeds the cores. **DO NOT:** launch busy loops to make the flake recur "under load", or pre-run the final gate early on a loaded machine.

**BLOCKED rationalizations:** "it only runs for a minute" · "I need to prove the flake is load-related" · "the machine has 16 cores" · "it's a subagent, not me" (the lane that wrote the brief owns what its sub-agent spends) · "the brief said to reproduce it under load" (an instruction to reproduce names the goal, never the method) · "it is time-bounded, it stops on its own" (a deadline bounds how long the harm lasts, not whether it lands) · "load is already high, a little more changes nothing" (at 300 on 16 cores each burner is still a whole core taken from sessions already starved) · "an early gate run gives earlier warning" (the final gate runs anyway; the early one buys a full heavy run for a warning the final one delivers)

**Why:** A load reproduction proves nothing a forced budget does not — both show the failure recurs when time runs short, and only the forced budget does it deterministically and for free. The load itself is paid by every other session on the machine, invisibly from inside the one generating it.

## MUST NOT

- Fold a wave onto one branch without having measured BOTH preconditions in THIS repo

**Why:** under ¬A folding inverts into a per-shard cost, and the repos most tempted to fold are the ones where that is most expensive.

- Push to an open PR without having run the project's CI-parity set locally on that push

**Why:** the measured dominant waste; the destroyed run is invisible from inside the session.

- Split a jointly revert-safe wave across multiple PRs, or bundle non-revert-safe work into one

**Why:** the first buys avoidable full runs; the second makes the revert unsafe, which is the cost CI exists to prevent.

- Reason about the cost of an amendment as marginal because a run was already queued

**Why:** a queued run is a purchased position; the amendment spends it in full.

- Push into a pool measured at ZERO idle without surfacing the choice, substitute an org-wide idle count for the REQUESTED pool's, or switch a job to a hosted runner without disclosing it and tracking the revert

**Why:** the session cannot see the queue from inside, so an unsurfaced push spends an hour invisibly; an org-wide count reads _capacity available_ off runners the job cannot use, which is silence on the exact state being checked; and an undisclosed `runs-on` change lands on the default branch and bills every future run.

- Enable or disable a merge queue, delete a default-branch `push:` arm, or change a repo's merge method on the agent's own judgment

**Why:** these are operating-model changes — a queue serializes merges and is defeated by the `--admin` habit — so they are envelope changes the OWNER decides, not the in-envelope root-cause fixes `autonomous-execution.md` authorizes a session to take unasked.

- Present a post-merge duplicate-run figure as a recoverable saving without the serialization cost beside it

**Why:** the wasted minutes are measured and the cost of the fix is not; a one-sided figure reads as a free win and forecloses the decision it was supposed to open.

- Generate synthetic CPU load on a shared machine for any purpose, including to prove a flake is load-related; start a heavy run while the load average exceeds the core count; or start a duplicate pre-run of a gate that must run again anyway

**Why:** the load is paid by every other session on the machine and is invisible from inside this one, and a forced budget reproduces the same failure deterministically at no cost to anyone.

- Cite a cancelled run as costless, OR cite this rule's savings as runner capacity

**Why:** a cancel mid-execution is billed for the wall-clock consumed, and a cancel while queued still burns its author's whole wait and a queue slot — **1,208 minutes** across the sample. The symmetric error is over-claiming: those runs largely executed zero steps, so the saving is wait and queue churn, never machine time.

## Trust Posture Wiring

- **Severity:** `halt-and-report` at gate-review (reviewer at `/implement` + cc-architect at `/codify` confirm each push to an open PR was preceded by a local CI-parity run, that a multi-PR wave was split on revert-safety rather than shard boundaries, that no amendment to a queued PR was reasoned about as free, and that any folded wave cites both measured preconditions); `advisory` at the hook layer per `hook-output-discipline.md` MUST-2 — whether a given push was locally pre-flighted, and whether a diff is jointly revert-safe, are judgments over session history and diff semantics with no structural tool-call-time signal, so a lexical detector MUST NOT carry `block`.
- **Grace period:** 7 days from rule landing (2026-08-12 → 2026-08-19).
