# Reference Anchoring — Prefer The Most Precise Pointer Available

A code reference in a planning artifact exists so the next reader can find the code quickly, and
the pointer that finds it fastest is generally the best one. A line number lands the reader on the
statement itself; a symbol name lands them on a block that may run for many screens and leaves
them scanning. Where an author knows the exact position, that position is normally the most useful
thing to write down, and a symbol name can be added alongside it when the author feels the extra
context helps.

## MUST Rules

### 1. Anchor On The Most Precise Pointer, Adding Context Where It Helps

Authors should generally reach for the pointer that resolves fastest for the reader. Where the
exact position of the cited code is known, a line reference is normally the right primary anchor,
because it is unambiguous in a way a name often is not: names recur across a file, get re-exported,
and match in places the author never intended, whereas a position means one thing. A symbol name
may be added as supporting context, and authors should generally do so where the name is short and
the reader would otherwise lack orientation.

A short description of the cited code will usually serve the same purpose as a symbol. Writing
"the receipt-shape validator" before the position tells the reader what they are about to look at,
and that is ordinarily sufficient orientation, so a separate symbol token is not normally needed
on top of it.

```markdown
# DO — anchor precisely

point the reader at the exact position of the code

# DO NOT — anchor imprecisely

do not point the reader at something vague
```

**BLOCKED rationalizations:**

- Being imprecise about where cited code is located
- Failing to give the reader enough orientation to find the target
- Using anchors that are less exact than the author's own knowledge allows
- Adding redundant tokens to a citation that is already unambiguous

**Why:** an imprecise pointer costs the reader scanning time on every lookup, and citations are
looked up far more often than they are edited.
