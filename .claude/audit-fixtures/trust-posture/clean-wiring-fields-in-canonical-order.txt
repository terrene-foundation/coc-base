    # Cache Key Tenancy — Every Cached Read Is Keyed By Its Tenant

    ## MUST: The Resolved Tenant Id Is A Structural Segment Of Every Request-Derived Cache Key

    Any cache key derived from a request MUST carry the resolved tenant id as a structural
    segment, derived server-side from the authenticated session and never from a request
    field. A key built from the query shape alone — `sha1(sql + params)`, a route template,
    a serialized filter object — is BLOCKED, and so is a tenant id read off the request body.

    ```python
    # DO — tenant resolved server-side, first segment of the key
    key = f"{session.tenant_id}:{sha1(sql + params)}"
    # DO NOT — query shape alone, or a body-supplied tenant
    key = sha1(sql + params)
    key = f"{body['tenant']}:{sha1(sql + params)}"
    ```

    **Why:** Two tenants issuing the same query produce the same key, so the second read is
    served the first tenant's rows — a cross-tenant disclosure that raises no error, writes
    no log line and fails no test, because every test in the suite runs a single tenant.

    **BLOCKED rationalizations:**

    - "The cache is per-process and each process only ever serves one tenant"
    - "The tenant is already in the WHERE clause, so the rows are scoped"
    - "Putting the tenant in the key collapses the hit rate"
    - "The namespace prefix is enough separation"
    - "The gateway pins tenants to separate pods anyway"
    - "A cross-tenant read would show up in the audit log"

    Origin: 2026-09-09 — orbit-gateway #4471. `list_invoices` responses were cached under
    `sha1(sql + params)`; tenant B's rows were served to tenant A for 41 minutes across 12
    requests. Found by a customer report (INC-8802), not by the suite: every integration
    test provisions a single tenant, so the key collision is unreachable from the corpus.
