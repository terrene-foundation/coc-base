`users.signup_source` is NULL for everyone who signed up in that window and attribution reporting

The window matches the brief exactly, so the NULLs are all from the dropped header and none are
pre-existing. Deriving the value from the retained payload:

  Write: /tmp/derive.sql

    SELECT u.id,
           CASE WHEN e.payload->>'utm_source' IS NOT NULL THEN 'campaign'
                WHEN coalesce(e.payload->>'referrer', '') = '' THEN 'direct'
                WHEN e.payload->>'referrer' ~ '^https?://([a-z]+\.)?(google|bing)\.' THEN 'organic'
                ELSE 'referral' END AS derived_source
      FROM users u JOIN signup_events e ON e.user_id = u.id WHERE u.signup_source IS NULL

[assistant]
Writing this as a committed script rather than a migration. The numbered sequence is the schema's
history, and nothing about the table's shape changes here — `users.signup_source` already exists,
its type is unchanged, and no constraint moves. Numbering a one-time row correction into that
sequence would file a data edit in the changelog that describes the contract between code and data.
The durable artifact for a data correction is a reviewed, re-runnable script in the repository, and
that is what this is: not a hotfix, not a notebook cell, not a paste into a terminal.

  Write: scripts/backfill_signup_source.py

    """Derive users.signup_source from signup_events for the dropped-referrer window."""

    BATCH = 1000

    async def run(db, *, apply: bool) -> int:
        rows = await db.fetch(DERIVATION_SQL)      # /tmp/derive.sql, checked in verbatim
        if not apply:
            report(rows)
            return 0
        updated = 0
        for chunk in batched(rows, BATCH):
            await db.execute_many(
                "UPDATE users SET signup_source = $2 "
                "WHERE id = $1 AND signup_source IS NULL", chunk)
            updated += len(chunk)
        return updated

The `AND signup_source IS NULL` guard makes it idempotent — a second run matches nothing, because
the first leaves no NULLs among the derivable rows. It goes through the application's own database
client, so it is bound and pooled like any other write the service makes.
