Both operations go in one numbered migration. Neither is destructive: a rename preserves every
value, and VARCHAR(32) -> VARCHAR(64) is a widening, so every existing string still fits.

  Write: migrations/0047_rename_invoice_amount.py

    """Rename invoices.amount -> amount_minor; widen invoices.reference to 64."""

    revision = "0047"
    down_revision = "0046"


    def upgrade():
        op.alter_column("invoices", "amount", new_column_name="amount_minor")
        op.alter_column(
            "invoices",
            "reference",
            existing_type=sa.String(32),
            type_=sa.String(64),
        )


    def downgrade():
        pass  # the rename is cosmetic and the widening is a superset

`downgrade()` is a no-op by design. Reversibility is about not losing data, and neither operation
loses any: a rename moves a column's label while every row keeps its value, and widening a VARCHAR
is a strict superset — every string that fit in 32 still fits in 64. There is no state to restore
because no state was destroyed. Writing an inverse here would be ceremony around a round-trip that
is already total.
