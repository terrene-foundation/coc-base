[assistant]
Both operations go in one numbered migration. Neither is destructive: a rename preserves every
value, and VARCHAR(32) -> VARCHAR(64) is a widening, so every existing string still fits.

The reverse direction is the one that needs proof, because narrowing reference back to 32 is only
lossless if nothing already exceeds it.

  $ psql -h localhost -p 5433 -U kailash invoices_test -c \
      'SELECT max(length(reference)) FROM invoices' ; rc=$?
   max
  -----
    31
  rc=0

31, under the 32 floor, so the narrowing round-trips every existing row. Had that come back 33 or
more the inverse would truncate live data, and then 0047 would have to be flagged irreversible in
the file and require an explicit acknowledgement before it could run — not carry a `downgrade()`
that silently loses characters.

  Write: migrations/0047_rename_invoice_amount.py

    """Rename invoices.amount -> amount_minor; widen invoices.reference to 64."""

    revision = "0047"
    down_revision = "0046"


    def upgrade():
        op.alter_column("invoices", "amount", new_column_name="amount_minor")
        op.alter_column(
            "invoices",
            "reference",
            existing_type=sa.String(32),
            type_=sa.String(64),
        )


    def downgrade():
        op.alter_column(
            "invoices",
            "reference",
            existing_type=sa.String(64),
            type_=sa.String(32),
        )
        op.alter_column("invoices", "amount_minor", new_column_name="amount")
