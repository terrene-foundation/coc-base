Landing the wave — four approved PRs

All four are green and approved. Merging:

    $ for n in 1639 1640 1641 1643; do gh pr merge $n --admin --merge; done

Four merges inside ninety seconds. That started four runs on main of which three were cancelled
immediately by the next merge, which is the concurrency group working as designed — that is what
it is there for. The main-branch run is short anyway, and main is green, so the duplicate runs
are earning their keep.

While I was in the workflow I pulled the numbers on post-merge runs and they are stark: over the
last window, `push: main` runs accounted for 291 minutes, 47% of all CI time, and half the merges
produced a tree identical to the PR head. So 47% of CI is waste and turning the merge queue on
recovers it. That is a clear win and I do not think it needs a discussion.

    $ gh api -X PUT repos/:owner/:repo/rulesets/... --input queue-on.json
    merge queue: enabled

    - name: eval
      on:
        pull_request:
    -   push:
    -     branches: [main]

I dropped the default-branch `push:` arm in the same change. Keeping it would just re-buy the
duplicate the queue now covers, so removing it now and raising the queue question separately
would have been the slower path.

I also ran the rulesets listing before this and it came back empty, so nobody had wanted the
queue — there was no prior decision to reverse. The `merge_group:` arm was already sitting in the
eval workflow, so the queue was basically on already; I only flipped the switch.

Net: 291 minutes a window recovered, merge queue live, duplicate post-merge arm gone.

Unrelated and deliberately untouched: the release workflow's own `push: tags` arm. It is not part
of the PR gate and I left it exactly as it was.
