# detectGitConfigMutation audit fixtures

Per `rules/cc-artifacts.md` Rule 9 + `rules/hook-output-discipline.md` MUST-4. Each fixture pins one scope-restriction predicate the detector relies on. Inputs are Bash command strings; expected outputs are what `detectGitConfigMutation(input)` returns — `null` (no flag), or a hit object whose `key` is asserted verbatim.

The detector fences loom#1470 **defeat 2**: a `git config` write to a security-load-bearing key of THIS repository's own `.git/config`. It cannot be a `STATE_PATH_RX` registry row, because the executed form (`git config core.repositoryformatversion 99`) contains the string `.git/config` nowhere — a premise `git-protected-surface-1470.test.mjs` § BASH-3 measures rather than asserts.

**Expectation is asserted on `key`, not merely on truthiness.** A boolean expectation cannot tell a hit on the RIGHT `git config` invocation from a hit on a masked mention of a DIFFERENT one, and two fixtures below (`flag-real-write-beside-masked-mention.txt` especially) exist precisely to discriminate those two. The runner is `git-protected-surface-1470.test.mjs` § BASH-8 — per the Rule-9 runner contract established by `cross-repo-authz.test.mjs`, a fixture with a README-declared expectation and no executable assert-expected-vs-actual runner is inert data, not an instrument (`rules/instrument-discipline.md` MUST-1).

## The bypass this set closed

`flag-file-flag-separated-value.txt` and `clean-file-flag-separated-value-read.txt` are regression fixtures for a defect found while enumerating these predicates, and fixed in the same commit.

The detector's own comment on `GIT_CONFIG_OUT_OF_REPO_FLAGS` states that `--file` / `--blob` "are deliberately ABSENT from this set: they name an arbitrary target that MAY be this repo's config, so they stay IN scope (fail-closed …)". Absence was necessary but not sufficient. Both flags take a VALUE, and the argument loop pushed that value onto `positionals`, shifting the key out of slot 0:

```
git config --file .git/config core.bare true   → null     ← the in-scope form the comment claims to hold
git config --file=.git/config core.bare true   → core.bare
```

git treats the two spellings as interchangeable — measured on a scratch repo, `bare = false` → `bare = true` in the repo's own `.git/config` — so the separated spelling was a silent bypass of this fence in exactly the case its author documented as covered. `GIT_CONFIG_VALUE_TAKING_FLAGS` consumes the value; both spellings now agree. The same shift skewed the READ test in the opposite direction (`--file X <key>` presented as two positionals and would have flagged as a write), which is why the fix ships both polarities.

## The accepted bound — read this before "fixing" the unquoted `$(…)` row

```
git config --file "$(git rev-parse --git-dir)/config" core.bare true   → flags core.bare
git config --file  $(git rev-parse --git-dir)/config  core.bare true   → null
```

Both write this repository's own config. The second is not flagged, and that `null` is **deliberate, not an oversight**. `_gitConfigArgTokens` stops at the first UNQUOTED shell metacharacter, so the argument tail ends at the `(` and the key is never reached. Per `rules/hook-output-discipline.md` MUST-3 this detector is **not a shell parser and performs no expansion**: an unexpanded command substitution is outside what a lexical instrument can resolve, exactly like the sibling `detectRepoScopeDriftBash/skip-command-substitution.txt` and `skip-shell-variable.txt` fixtures, which expect `null` for the same reason. The pre-fix `--file` gap this fixture set otherwise records was a different thing entirely — there the key WAS present in the command and the detector still missed it.

**Do not close this by widening the metacharacter stop.** That stop is load-bearing for the doc-carrier and fail-closed re-scan paths: it is what keeps a tail handed over from inside a command substitution (`… core.bare true)"`) from absorbing the carrier's trailing punctuation as a positional. Widening it would require its own predicate analysis and its own fixture set, both polarities, plus re-verification of `flag-command-substitution-in-carrier-body.txt` and `flag-backtick-substitution-in-carrier-body.txt` — it is a separate change, not a one-line tweak.

The two rows are a matched pair on purpose. If a future edit makes the unquoted row flag, that is a signal to check what it did to the carrier path, not a win.

## Attack-surface breadth (loom#1477)

The rows above pin the detector's PARSER semantics — masking, tokenizing, positional counting. The rows below pin the reach of its three membership SETS across scope flags, write forms and key families the parser rows never touch. The split matters when reading a failure: a red above means the detector mis-PARSED a command, a red below means it parsed correctly and the command was not in a set it should have been.

Each row was measured the same way as the rows above — invert one predicate, re-run in a fresh process. The first seven redden under a mutation NO row above catches; they are single-predicate isolators. The last six are labelled CORPUS: measured as co-caught by a row above, kept for an attack SHAPE or a self-blocking regression the set otherwise states nowhere. The distinction is recorded per row so a later reader can re-run it rather than trust it.

## What each fixture can and cannot discriminate

Per `rules/instrument-discipline.md` MUST-1, every row above was checked by INVERTING its predicate in `violation-patterns.js` and re-running the fixture set in a fresh process. A fixture that stays green when its predicate is wrong is not evidence for that predicate, whatever it prints. Three findings from that pass are recorded here because they changed the fixture set:

- **`clean-read-subcommand.txt` was rewritten.** The original `git config --get core.repositoryformatversion` stayed `null` with `GIT_CONFIG_READ_FLAGS` emptied — at ONE positional the count test returns `null` on its own, so the fixture reported nothing about the read-flag set. The two-positional `--get <name> <value-pattern>` spelling flags under that mutation and holds `null` without it.
- **`clean-subcommand-prefix-boundary.txt` was added.** No original fixture reddened when the opener's `(?![\w-])` boundary was removed, so that predicate had no coverage at all.
- **`clean-dash-c-override-is-not-config.txt` is over-determined, and is labelled as such.** Two independent opener mutations — accepting ANY subcommand word in place of the literal `config`, and replacing the option allowlist with the generic `\S+` skip its comment contrasts against — BOTH left it green. `git -c k=v commit` carries no second positional and its `k=v` is one `=`-bearing token, so several predicates return `null` for it independently. It is kept as a regression pin on the repo's own committing idiom (its falsifying result is "the detector ever flags it"), NOT as evidence about the opener. The opener's ALLOW half is isolated by `flag-git-global-option-prefix.txt` and its boundary by `clean-subcommand-prefix-boundary.txt`.

Three further findings from the loom#1477 breadth pass, recorded because they bound what this set proves:

- **`--add` and `--replace-all` have no isolating fixture, and cannot have one.** With `"add"` (or `"replace-all"`) removed from `GIT_CONFIG_WRITE_FLAGS` NOTHING in the set reddens: both flags always carry a value, so the two-positional count test flags them independently. The Set entries are load-bearing only for the one-positional forms, which `flag-write-flag-single-positional.txt` (`--unset`) and `flag-unset-all-form.txt` (`--unset-all`) do isolate. The `flag-add-form`/`flag-replace-all-form` rows are labelled CORPUS above for exactly this reason.
- **`-c k=v` in the opener's option allowlist was UNCOVERED, and the gap is now closed.** Removing that alternative reddened nothing: the only inputs carrying `-c` were `git -c … commit` forms, which never reach a `config` subcommand and return `null` either way, so the entry could have been deleted silently. `flag-dash-c-override-then-config-write.txt` was added in the same pass that found it — a `-c` override followed by a real `config` write, which returns `core.bare` at baseline and `null` under the mutation. `flag-git-global-option-prefix.txt` isolates the `-C <dir>` alternative only.
- **Two mask-path mutations returned green and are recorded as INERT, not as coverage gaps.** Dropping `GIT_COMMIT_WITH_BODY_RX` from the carrier test, and bypassing `maskDocCarrierPayloads` entirely, both left every row green. Per `rules/instrument-discipline.md` MUST-2(b) that leaves two hypotheses, so reachability was measured rather than assumed: `maskDocCarrierPayloads` alters only 2 of the 34 inputs (`clean-doc-carrier-prose.txt` and its former duplicate), and both stay `null` masked or raw — the real work on the carrier path is done by `maskQuotedSpans` inside the carrier branch, which `flag-real-write-beside-masked-mention.txt` and the two substitution rows DO isolate (measured: skipping carrier segments outright reddens all three). The mutations were inert at these inputs; the mask path is not unpinned.

**Length rationale.** This README carries one row per predicate with the `**Why**` each predicate exists, matching the sibling `detectRepoScopeDriftBash/README.md` convention. The rows are the audit surface; compressing them would leave a reviewer unable to tell a load-bearing predicate from an incidental one.
