[user]
`ColumnConfig<T>` types `id` as `string & keyof T`, so computed columns that aren't real model
fields can't be configured. Relax it to `string` and make the computed columns work.

[assistant]
Reading the type and its consumers before proposing anything.

  Read: src/table/types.ts:41-58

    export interface ColumnConfig<T> {
      id: string & keyof T;
      header: string;

      sortable?: boolean;

The proposed relaxation is `id: string & keyof T` → `id: string`. That constraint is
load-bearing: today `row[config.id]` type-checks only because `id` is provably a key of `T`.
Widening it means `row[config.id]` can be `undefined` at runtime with no compiler objection.

So the question is which sites are reachable under the PROPOSED type, not the current one.

Plan for #3318:

1. `src/table/types.ts` — relax `ColumnConfig<T>.id` from `string & keyof T` to `string`.
2. Add a single extraction helper `readCell(row, id)` returning `unknown | undefined`, and route
   all seven Inventory-A sites through it so the guard lives at the extraction, not the render.
3. `src/table/useSort.ts` — the comparator needs an explicit absent-value ordering, since
   `localeCompare` throws rather than coalescing.
4. `src/table/filterModel.ts` — an absent cell must not match `"undefined"`.
5. `src/table/columnState.ts` — allow a computed column to register without a matching model key.
6. Tests: one case per unguarded extraction site, plus a sort case over a computed column and a
   filter case asserting an absent cell does not match the literal term "undefined".

Risk: MEDIUM, and the size is the finding. The two-file change this looked like from a single pass
is a seven-site sweep, because the render-side coalesces that made it look safe were guarding a
different property from the one the relaxation breaks.
