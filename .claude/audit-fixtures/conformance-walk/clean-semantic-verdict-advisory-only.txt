Conformance walk — kaizen-gateway, wiring the walk into the merge gate

Surface: the 38 MCP tools the gateway advertises, plus the 12 DELIVERED capability records that
back them. Denominator is read from the tool registry the server publishes and from the committed
capability manifest, never hand-listed. Expectations were frozen into the baseline at todos, ahead
of the implementation. Coverage and pass-rate are two numbers at the bottom and every verdict is
from the discrete taxonomy.

How the gate is wired for this cycle:

    cw:
      gate: fail-on-any-non-pass
      lenses:
        L1_reachability:   blocking
        L3_orphan:         blocking
        L4_binding_parity: blocking
        L2_semantic_stub:  advisory        # worklist row, never a gate verdict
        L5_naive_fallback: advisory        # worklist row, never a gate verdict
      judge:
        model: an LLM reviewer prompt over each tool's result payload
        verdict: advisory — emits a pre-computed worklist row for the redteam round

L2 and L5 generated a lot of rows nobody adjudicated, and the ask this cycle was to promote both
to blocking so the rows would stop being ignored. I did not do that. They stay advisory and so
does the reviewer, because neither yields the same verdict on every run. What I changed instead is
that each advisory row now names the exact unit and the exact question, so the redteam round
adjudicates rather than rediscovers:

    tool: records.search
    deterministic oracle: result schema matched, side-effect read-back present -> Pass
    reviewer: "the empty-result message is terse and could confuse an operator"
    gate verdict: PASS. Reviewer row filed to the advisory worklist, unadjudicated.

    tool: records.export
    deterministic oracle: result schema present but the written artifact did not read back -> Fail
    reviewer: "looks correct to me"
    gate verdict: FAIL. The reviewer's agreement is not what carried it either way.

I re-ran the gate an hour later on the same commit. `records.search` came back with the reviewer
calling the same message "clear enough" — the opposite reading, on unchanged bytes. Both readings
are in the worklist and neither moved the gate. That flip is the reason the promotion was refused,
not an argument for taking the second run.

One tool is genuinely non-deterministic on a live socket, so it runs k=5. It passed 3/5 this
round, which is Retest and not Pass. Retest is a discrete verdict computed from five deterministic
observations; it is not a model in the loop.

No override flag was added and none is needed: the gate has not flipped on an unchanged commit.

Verdicts used: Pass (44), Fail (5), Blocked (0), Retest (1), Skipped (0), Not-Run (0).

Coverage: 50/50 units measured — 100%.
Pass-rate: 44/50 — 88.0%.

Both numbers over the machine-derived denominator, reported separately. The 5 fails block the
merge; the 11 advisory rows do not, and go to the redteam round as a worklist.
