Measuring before answering.

    $ node scripts/measure-replica-lag.mjs --window 24h
    samples 41,208    p50 180ms    p95 4.1s    p99 47s    max 61s

    $ cat config/cache.yml
    search_list:
      source: replica
      ttl: 60
      invalidate_on: []

    $ rg -l "searchList\(" src/api/ | wc -l
    6

Recommendation: route the search list to the primary — the one database everybody
writes into — for the first 10 seconds after a write, and leave the read-replica —
the second copy we read from so the main one is not overloaded — serving everything
else.

Why this one: the staleness is replication lag, the delay before an edit reaches
that second copy, not a TTL problem, TTL being how long we keep a cached answer
before throwing it away. Worst-case-in-a-hundred lag — p99 — is 47s against a 60s
TTL, so raising or lowering the TTL moves a number that was never the binding
constraint. The 10s primary window covers all but the slowest 5% of edits and leaves
the replica carrying the other 99.4% of search traffic.

Implications:

- Reads inside the 10s window hit the primary, so requests-per-second on it rise
  about 6% at current traffic — well short of connection pool saturation, which is
  running out of simultaneous database connections and is what would make the app
  hang rather than merely lag.
- Read-your-writes consistency — the guarantee that you always see your own edit —
  becomes certain for the editing user; everyone else keeps seeing the change arrive
  a beat late, bounded by the replication lag above.
- Ongoing: the TTL stays at 60 but stops being load-bearing, because cache
  invalidation — deliberately throwing the cached answer away when the underlying
  shift changes — now fires on write rather than on expiry.
- Reversibility: config-only, one key in cache.yml, no migration, no deploy gate.

Cons:

- Sticky routing — keeping one person's requests on the same server — has to hold
  for the whole 10s or the guarantee is partial. Our load balancer pins by cookie
  and the pin drops on a new tab, so an edit in one tab and a search in another
  still reads the replica.
- The 6% headroom is a quiet-hours figure. Tuesday 08:00 peak runs three times the
  traffic, where the same window costs 18% — inside the pool, but not comfortably
  inside it.

Both cons point the same way: if the Tuesday peak tightens further, the window
shrinks to 5s before anything else changes.

Go ahead with the 10-second primary window? (yes/no)
