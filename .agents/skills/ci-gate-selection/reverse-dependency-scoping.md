# Reverse-Dependency Scoping — The Closure, The Fail-Open Contract, The Calibration

Depth companion to `SKILL.md` §2. Read before building a diff-scoped selector for a new corpus.

Reference implementation: kailash-rs `scripts/ci/clippy-scope.mjs` (252 lines) and `scripts/ci/job-crate-scope.mjs`. **Cited, not vendored** — those files belong to that repo, are not distributed by loom's manifest, and are named so the prior art is findable, not liftable.

## 1. Why REVERSE dependency, and not "the packages the diff touched"

The touched set is not the broken set. Changing package `core` cannot break `core`'s dependencies; it can break everything that depends on `core`. The closure to compute is therefore the **reverse** one — the transitive dependents — and it is the smallest set that is provably sufficient.

Two consequences worth stating because both are counter-intuitive at the moment of authoring:

- **The closure of a leaf is tiny and the closure of a hub is nearly everything.** That is not a defect of the algorithm; it is the true shape of the risk. See §4.
- **The closure is over the DEPENDENCY graph, not the directory tree.** Two packages in adjacent directories may share no edge, and a package three directories away may be a direct dependent. A path-prefix heuristic is a different, weaker instrument that happens to agree with the closure on tidy repos — which is exactly how it survives review.

## 2. The pipeline, step by step

```text
git diff --name-only <merge-base>...HEAD          ← three-dot; two-dot on a branch behind
        │                                            base renders base's commits as
        ▼                                            reversions (evidence-first-claims MUST-5)
path → owning package                             ← resolved against the workspace manifest,
        │                                            never a hand-kept prefix list
        ▼
touched packages → transitive DEPENDENTS          ← the reverse closure
        │
        ▼
emit as gate arguments (-p a -p b …)              ← selection for the LINT/TEST gate
        │
        └─► a SECOND resolver decides which JOBS run at all, from the same closure
```

Keeping job selection in a second script matters: it is what lets an irrelevant job be skipped by a per-JOB `if:`, which still reports a terminal `skipped` conclusion, rather than by a workflow `paths:` filter, which reports nothing and wedges a required context forever (`rules/ci-job-budget.md` MUST-2).

## 3. The fail-open contract

**Every unresolvable input widens the run. There are no exceptions, and the widening is silent-free — it should say why it widened.**

Inputs that MUST widen:

| input | why it cannot be resolved to a package |
| --- | --- |
| lockfile (`Cargo.lock`, `package-lock.json`, …) | a dependency version change reaches everything |
| root / workspace manifest | membership, features, or shared profile changed |
| a path under no known package root | a new package, or a mapper gap — indistinguishable |
| CI configuration, shared build scripts | they define how every package is built |
| a rename or move the mapper does not model | the old and new owners may differ |

In the reference measurement, **5 of 17 real commits resolved FULL, and all five touched `Cargo.lock` or the root manifest** — the fail-open path firing exactly where it should, on a fifth of real traffic. A selector whose fail-open path never fires on real traffic has probably not implemented one.

**Why closed-fails are the whole risk.** A selector that fails closed turns each of its own path-mapping gaps into a skipped gate that reports green. That is `rules/verification-gate-integrity.md` MUST-2's absence-reads-as-a-pass, generated by the very mechanism intended to make the gate affordable.

## 4. The bimodality, and designing for two regimes

Measured over 81 workspace packages:

```
min 1  ·  p25 2  ·  median 6  ·  p75 18  ·  p90 30  ·  max 46  ·  mean 11.7
65% of crates reach ≤10% of the workspace
 9% of crates reach >50%
 7 hub crates reach 42–46 of 81
```

`mean 11.7` against `median 6` is the tell: the mean is dragged by a hub tail that no policy can narrow. Do not size a policy on the mean.

**Two regimes, two designs:**

- **Leaf regime (the common case).** Narrow aggressively. The median 93% reduction is real and is where the entire saving lives.
- **Hub regime.** Accept the full run. A partial run on a hub touch is a worse instrument than the full one AND cheaper than it by almost nothing — 46 of 81 is not a saving worth a new failure mode. Building a clever partial hub policy is effort spent making the riskiest changes less well tested.

A useful shape for the decision, stated as a question rather than a constant: *does this package's closure exceed the point where the residual saving stops paying for the risk of getting selection wrong?* That point is per-corpus (§5), which is why no number is written here.

## 5. Calibration — the procedure, because the constants do not travel

**The instrument transfers; the numbers do not.** loom's own `.claude/bin/owed-suites.mjs` pins `FANOUT_MAX = 3`: a file referenced by more than three suites is reported BROAD and gets no named owner. Against loom's artifact graph (p90 8, max 55) that is a defensible line. Against a sibling repo's source graph (p90 15, max 160) the same constant would **refuse 44.3% of its modules** — all BROAD, all unowned, the instrument silently answering "nobody owns this" for nearly half the corpus. Same logic, same constant, opposite verdict.

Before any threshold is written into a selector for a new corpus:

1. **Enumerate the population from the authority** — the workspace manifest, the module graph, the package index. Not a directory listing, and not a hand-kept list.
2. **Compute the full closure-size distribution** across that population. Report min / p25 / median / p75 / p90 / max AND the mean, so the hub tail is visible.
3. **Name the falsifying result before reading it** (`rules/instrument-discipline.md` MUST-1): if scoping were not worth building here, this instrument would print a median close to the population size and a p25 already large — i.e. almost every change reaching almost everything.
4. **Identify the hub set explicitly** and decide the hub-regime policy before writing any threshold.
5. **Re-derive on graph change.** A new shared crate, an extracted utility, or a dependency inversion moves the whole distribution without a single threshold changing — the same re-derivation obligation `rules/ci-job-budget.md` MUST-3 places on its census.

## 6. Controls — a selector is two-poled, per arm

The reference carries **12/12 controlled arms** on the scope resolver and **16 arms with both `run=true` and `run=false` reachable** on the job resolver. The second shape is the one to copy.

A selector control that only ever demonstrates `run=true` proves the selector can say yes. It says nothing about whether the selector can correctly say NO — and "incorrectly says no" is the only failure mode that costs anything, because it is the one that skips a gate. Both poles, per arm, is the contract; `rules/instrument-discipline.md` MUST-3(a) is the general form and `.claude/audit-fixtures/_lib/arm-coverage.mjs` is this corpus's mechanisation of it (an arm is a DECLARED ROW that must produce a firing, not a regex branch the author remembers to control).

**The specific trap:** widening the path→package mapper to handle a new layout adds an arm. If no control row is added with it, the mapper now has a branch that has never been shown to fire, and its silence on that branch is indistinguishable from a correct empty result.

## 7. Which axis to scope on

Scope on the axis your build system CHARGES you for.

Measured on kailash-rs: a one-line leaf change costs **16–17s of recompile** against **40.8s to RUN one crate of 48**. Warm, the run dominates — and only package-level selection cuts compile and run together. Narrowing which test FUNCTIONS execute leaves the compile fully paid and moves a minority of the bill.

That inverts in a corpus with no compile step, where the test-file or test-function axis may be the only axis there is. The rule is the question, not the answer: measure what the gate spends before choosing what to narrow.
